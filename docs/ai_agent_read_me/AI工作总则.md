# AI 工作总则

本文只记录跨模块、跨任务都适用的协作原则。环境命令、代码格式、Git 操作、版本发布和打包细节不在此重复，具体工作按本目录 `README.md` 的导航阅读对应专项文档。

## 专项任务查阅规则

需要为具体工作寻找实现方案、操作步骤或验收标准时，必须先打开本目录的 `README.md`，按任务类型定位并完整阅读对应专项文档，再检查源码并执行。不要只凭本总则、旧聊天记录或经验补全专项流程。

如果一项工作同时涉及多个领域，应同时阅读相关文档。例如“修改热更新后打包并提交 PR”需要阅读版本更新、打包部署和提交 PR 三类文档。

## 信息优先级

处理任务时按以下优先级判断：

1. 用户在当前任务中的最新明确要求。
2. 当前源码、配置、资源、测试和实际调用链。
3. 仓库内对应专项文档。
4. 旧聊天历史、经验和未经验证的推测。

如果文档与当前实现冲突，应核对真实行为并指出冲突；不能为了符合旧文档而直接覆盖用户的新实现。

## 协作原则

* 默认把实现请求完成到修改、验证和结果说明；用户明确要求“先说计划”时才停在方案阶段。
* 不擅自回滚、覆盖或整理用户已有改动。无关内容应隔离，相关内容应保留原意后整合。
* 修改前先找到真实入口、配置来源、数据生成位置、运行时消费位置和打包路径，避免只修表面调用点。
* 功能按可以独立说明、验证和回滚的边界拆分；纯格式修改不能掩盖功能差异。
* 用户指定文件范围、标题措辞、保留项或“不恢复”内容时，按用户原话执行。
* 新增运行时配置或资源格式时，同时检查生成器、读取方、默认模板、打包流程和测试。
* 声称一个参数影响多个阶段时，应逐条核对每条调用链。例如“自动携带”和“智能使用”必须分别验证。
* 测试范围与风险匹配。无法运行的检查、依赖外部环境的行为和仍需用户裁定的事项必须明确说明。
* 不把聊天历史当成长期规范的唯一载体。可复用规则应写入对应专项文档，具体行为应尽量由代码和测试固定。

## 完成标准

任务完成至少满足：

* 用户要求的行为已经实际实现，不只停留在说明或半成品。
* 相关调用链、配置和资源边界已经核对。
* 已执行最小但有效的测试与格式检查，或明确说明无法执行的原因。
* 没有夹带与当前任务无关的工作区改动。
* 对外行为、开发流程或数据格式发生变化时，对应专项文档已经同步。
* 用户要求 PR 时，必须先按 `README.md` 的导航阅读提交与版本相关文档，再完成创建、远端审核、合并和本地同步。
