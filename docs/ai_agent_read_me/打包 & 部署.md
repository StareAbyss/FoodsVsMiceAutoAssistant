# 打包与部署

本文说明发布包的打包、安装、调试和卸载流程。源码开发运行方式见 `项目运行环境和调试环境.md`。

## 打包

发行打包应从干净的 tag / PR merge commit 工作区执行。推荐在项目根目录上一级使用：

```text
_biuld/
```

作为临时构建工作区。打包结束后，`_biuld/` 内的临时 worktree 或源码拷贝可以删除。

发行产物输出到项目根目录上一级：

```text
_dist/
```

`_dist/` 是产物归档区，只能新增，打包脚本不会删除旧产物。每次打包会新建类似下面的目录：

```text
FAA-v3.1.1 2026-06-07 15-39-33
```

Windows 文件夹名不能包含英文冒号，因此时间使用 `HH-mm-ss`。

完整发行包先在源码根目录的 `dist/FAA/` 准备，复制归档到上级 `_dist/` 并通过发行校验后自动删除此暂存副本；复制或校验失败时保留暂存内容。其他 `dist/` 子目录不受影响。

在要打包的干净源码根目录运行：

```powershell
python 一键生成分发资源.py
```

如当前 shell 没有可用 Python，先按 `项目运行环境和调试环境.md` 配好 `.venv` 或使用：

```powershell
uv run python 一键生成分发资源.py
```

如果从开发工作区运行脚本，但希望打包 `_biuld/` 中的干净源码，可以设置：

```powershell
$env:FAA_PACKAGE_SOURCE_ROOT = "F:\...\_biuld\FAA-v3.1.1"
uv run python 一键生成分发资源.py
```

脚本会检查 `FAA_PACKAGE_SOURCE_ROOT` 对应源码是否处于带 tag 的 GitHub PR merge commit，检查不通过会中断。

## 普通用户启动入口

发布包中普通用户运行：

```text
FAA - 快速启动.exe
```

`FAA - 快速启动.exe` 是 x64 原生快速启动入口，仅调用已有的 `.venv/Scripts/pythonw.exe` 启动 FAA 并等待本次任务的主窗口就绪，不安装 Python、不执行 uv、不同步依赖。缺少环境、进程提前退出、启动错误窗口或等待主窗口超时时，自动打开同根目录的 `FAA - 环境安装器.exe`，展示失败原因和日志，等待用户自行操作安装或修复。找不到环境安装器时显示明确的缺失路径。只在主窗口就绪前监测故障，正常运行后的退出不会触发修复。两个 EXE 均只使用 Windows 系统 DLL，不依赖 .NET。

FAA 内重启和命令行恢复完成使用 `FAA - 快速启动.exe`；启动 EXE 时直接传递参数，不经 Shell 解析。指定入口不存在时明确报错。热更新完成后不自动启动 FAA 或安装器，提示用户自行运行目标版本的 `FAA - 环境安装器.exe`，准备环境后再启动。

启动器源码和构建脚本位于：

```text
tool\faa_launcher\launcher.cpp
tool\faa_launcher\build.ps1
tool\faa_launcher\build_faa_launcher.ps1
```

需要重新生成启动器时运行：

```powershell
powershell -ExecutionPolicy Bypass -File tool\faa_launcher\build_faa_launcher.ps1 -Cxx "D:\Dev\Tools\Dev-Cpp\MinGW64\bin\g++.exe"
```

## 发行布局与校验

发行包与热更新暂存包统一使用 `function/common/distribution_layout.py` 中的白名单和校验函数。本地发行打包使用所选源码中的规则；热更新由下载目标源码中的 `plugins/updater/prepare.py` 在隔离 Python 子进程中加载目标版本的规则，不能使用正在运行的旧 FAA 已导入的同名模块。

| 项目 | 源码中的位置 | 用户目录中的位置 | 校验 |
| --- | --- | --- | --- |
| 普通启动入口 | `plugins/root_entries/FAA - 快速启动.exe` | 根目录 `FAA - 快速启动.exe` | 必需且非空 |
| 环境安装器 | `plugins/root_entries/FAA - 环境安装器.exe` | 根目录同名文件 | 必需且非空 |
| 内置 uv 包 | `plugins/launcher_scripts/uv/uv-x86_64-pc-windows-msvc.zip` | 同相对位置 | 必需且非空 |
| 更新执行核心 | `plugins/updater/updater.py` | 同相对位置 | 必需且非空 |

源码中的 `plugins/root_entries/` 是两份正式 EXE 的统一分发来源。构建会同步写入此目录，打包仅按白名单复制这两个文件到用户根目录，不整体复制入口目录。构建 PS1、诊断工具以及本机 `bin` 缓存不进入发行包。

`plugins/launcher_scripts/` 只分发上述固定 uv ZIP，不整体复制目录。uv 0.6.12 的 ZIP SHA256 为 `30FDF26C209F0CB7C97D3B08A26AB4E78CE5AE0E031B88798CBACCC0F24F452B`；原生入口解压前核对 hash，再调用 Windows 自带的 tar 安装到本地 `bin/uv.exe`。

发行前先验证源码中的两个成品 EXE 和 uv ZIP，再生成复制计划，最后才清理工作输出目录。复制完成后按同版规则验证关键文件与目录，文件必须是非空文件。热更新的包含项、排除项、目录映射及必需项均由目标版本决定；当前运行版本只负责下载、解压和调用目标准备入口，不再按旧版文件名检查新版。缺失目标文件时中断准备，不从当前安装补入旧启动脚本或旧入口冒充目标版本。

用户侧不分发 BAT 或 PS1 运行入口。构建保留 `tool/faa_launcher/build.ps1` 和 `tool/faa_launcher/build_faa_launcher.ps1`；OpenCV 诊断 BAT 仅作为开发工具保留，不纳入普通用户包。

源码归档中的少量旧路径过渡文件仅供已发布旧更新器读取，正常发行白名单不复制它们。旧用户选择包含过渡支持的新版本后，原生入口自动从首次原始备份按目标规则完成更新，并清理根目录过渡文件，无需手动覆盖修复包。不可变旧流程使首次过渡多一次精确 commit 源码下载，后续使用新协议的更新不需要这一步；细节见[原生入口说明](../../tool/faa_launcher/README.md#已发布旧版本的自动更新过渡)。

## 热更新的准备与替换

下载前先根据当前版本大小预估空间；源码 ZIP 解压到 `update_cache/staging_work/source/`，目标版本的独立准备入口只依赖 Python 标准库，以现有 Python 的隔离进程执行。它按目标发行布局生成候选目录，调用目标版本的用户数据迁移规则，再写入迁移报告、版本状态和更新计划。用户取消替换时，当前安装目录不受影响。

此阶段不安装新版运行依赖，也不导入 FAA 图形界面。若现有 Python 无法执行目标准备入口或迁移代码，准备会停止并保留当前版本，不能先替换文件再等待环境安装器补救。

准备成功后保留纯净目标源码，不能只保留已经迁移过用户数据的候选目录。用户确认后，将候选目录中的目标 `updater.py` 复制到临时目录执行；该进程等待 FAA 退出，再用纯净目标源码重建候选版本，并重新迁移退出时保存的最终配置，复核实际空间。这样确认期间的用户配置修改不会被预览阶段的旧副本覆盖。最终准备失败时保留计划与源码供重试，不能把半成品当成可替换版本。

普通更新 CLI 与同目录的原生启动、安装和恢复共用互斥锁，避免最终迁移期间通过快速入口重新打开 FAA。无法取得锁时停止本次操作，不覆盖正在执行的另一轮更新状态。旧版过渡和图形恢复由原生父进程持锁，子脚本不重复申请同一锁。

更新进程等待的是发起更新的 FAA 进程，不会按进程名称强制结束其他窗口。更新前应关闭同目录下其他已经运行的 FAA 实例；上述互斥锁阻止的是更新期间通过原生入口新发起的操作。

只有最终准备成功后才备份并替换版本区；失败时尝试回滚。普通更新保留 `.venv/`、`backups/`、`update_cache/`，环境安装器随目标版本一起替换。恢复备份则保留正在运行的安装器及明确指定的日志。更新成功后清理本轮纯净源码缓存，并提示用户自行运行环境安装器，不自动安装依赖或打开 FAA。新版 FAA 启动时再按自身模板和方案协议处理格式兼容。

## 原生图形安装器

启动器源码位于 `tool/faa_launcher/`，操作、构建和验证说明见该目录的 `README.md`。
构建在 FAA 根目录生成 `FAA - 环境安装器.exe` 和 `FAA - 快速启动.exe`，均为 x64 原生程序。

启动器构建中间文件使用 `dist/faa_launcher/build-随机标识/` 独立目录。编译和成品复制全部成功后自动清理本次中间文件，失败时保留并输出路径；根目录、`plugins/root_entries/` 和自定义输出目录中的成品不在清理范围内。

`FAA - 环境安装器.exe` 提供安装并启动、卸除运行环境和恢复备份，左侧步骤随操作切换。调试启动放在“额外设置”，日志可在右侧放大并持续显示。
普通启动和恢复后的普通启动确认本次 Windows Job 内的 FAA 主窗口就绪后自动关闭安装器，兼容 Python 虚拟环境启动跳板派生子进程的情况，主程序继续独立运行；调试启动保留日志窗口。加载窗口、本次启动任务之外的窗口和启动失败提示不会触发自动关闭。

运行环境检测统一放在依赖同步完成、启动 FAA 主窗口之前，安装和恢复备份共用。检测系统与 Python、锁定依赖、启动资源、目录写入、Qt、图像处理、Windows API 与加密、业务依赖及 ONNX；GPU、WMI 服务、CBC 求解器和 OCR 扩展作为可选能力提示。必需项失败时暂停并显示处理建议，可重试或修复依赖；仅有可选提示时允许用户确认后继续启动。检测脚本 `tool/faa_launcher/runtime_probe.py` 内嵌于 EXE，使用独立隐藏进程隔离故障，不读取凭据或执行游戏操作。具体检测范围与验证命令见[原生安装器说明](../../tool/faa_launcher/README.md#统一运行环境检测)。

发行资源清单与更新暂存清单不包含独立支持性检测 BAT。
两个程序都只能从自身所在的 FAA 根目录运行。启动器通过 `LICENSE`、`uv.lock`、`pyproject.toml` 和 `function\faa_main.py` 检查位置；标识不齐时会显示红叉并锁定操作。
界面使用原生 C++、Win32 控件和系统 GDI+，不依赖 .NET、Qt 或额外安装的 VC++ 运行库。
正式安装会准备根目录中的 `.venv`，建议在独立发行包副本中使用，避免移除源码开发环境的开发依赖。
两个下载源选择框都支持预设和自定义网址。
使用安装包指定依赖源时执行 `uv sync --locked --no-dev`；选择其他源时，先用 `uv export --locked --offline --no-dev --no-emit-project` 导出版本及 hash，
再用 `uv pip sync --require-hashes --strict` 从指定源安装。安装器不修改原始 `pyproject.toml` 和 `uv.lock`，详细流程见原生安装器的 `README.md`。

原生安装器不使用 BAT 或 PS1 运行入口，不打开额外控制台。卸除通过 Windows API 在主页面处理确认、进程占用和受限目录删除，范围仍为项目内 `bin` 与 `.venv`。
恢复页面显示备份版本、时间和当前版本，确认后先备份当前文件，再恢复程序文件及配置。`plugins\updater\updater.py` 在构建时内嵌到 EXE，并通过隐藏的 Python 进程执行 `restore --gui --launch ""`，阶段和日志回传界面；恢复时保留安装器、`.venv`、备份、缓存与日志。文件恢复完成后按恢复版本的锁文件同步环境，再由原生安装器启动 FAA。恢复阶段不允许强制取消，以便更新器完成恢复或回滚。
备份查看、详情和删除统一在原生安装器的“恢复到备份”页面提供，列表按修改时间排序，详情包含版本、Tag、PR、提交号、大小和路径。删除经过单独确认，支持清理不完整备份，并限制在当前 `backups` 内，不跟随目录链接。FAA 内保留原有更新列表、下载、迁移和更新执行；更新页的“查看相关说明”独占第三行，不提供备份管理窗口。

构建普通入口和正式安装器时会同步生成 `plugins/root_entries/FAA - 快速启动.exe` 与 `plugins/root_entries/FAA - 环境安装器.exe`，发行包和源码暂存包按入口白名单将它们放到根目录。普通更新部署目标版安装器；由安装器发起的备份恢复保留正在运行的安装器，避免移动被占用的程序。

## 调试、卸除与恢复

在 `FAA - 环境安装器.exe` 的“额外设置”中开启调试启动，FAA 打开后保留并展开日志面板，不打开额外控制台。

卸除操作仅删除当前 FAA 的 `.venv` 与 `plugins/launcher_scripts/bin`；配置、资源、全局 Python 和全局 uv 保留。恢复和备份清理由安装器的备份页面提供，使用受限路径检查并在必要时处理进程占用。

## 依赖和镜像策略

`pyproject.toml` 分别配置 Python 本体和 Python 依赖包的下载源：

```toml
[tool.uv]
python-install-mirror = "https://registry.npmmirror.com/-/binary/python-build-standalone"

[[tool.uv.index]]
url = "https://pypi.tuna.tsinghua.edu.cn/simple"
default = true
```

`uv python install` 使用 `[tool.uv].python-install-mirror` 中的 npmmirror 下载 Python 本体。该字段缺失或无法读取时，uv 会使用默认源（GitHub 源）。

`uv sync` 使用 `[[tool.uv.index]].url` 中的清华 PyPI 镜像下载 Python 依赖包。两个原生入口直接读取以上配置，环境安装器还允许用户在界面中选择下载源。

`uv.lock` 中的版本和 hash 是依赖完整性的依据。镜像源可以按网络情况调整，但发布安装流程不应重新解析依赖或随意改写 `uv.lock`。

发布或用户安装入口必须使用：

```powershell
uv sync --locked --no-dev
```

开发者更新依赖时，在开发环境中执行 `uv add`、`uv remove` 或 `uv sync` 并检查结果。提交依赖变更时，应同时包含 `pyproject.toml` 和 `uv.lock`。

## 图像资源与本地凭据

图像资源数据库凭据保存在项目根目录：

```text
image_resource_db.local.json
```

该文件只属于维护者本地环境，必须保持在 `.gitignore` 中，不提交到 GitHub，也不复制到发行包。不要把数据库凭据改回普通用户必须配置的环境变量。

图像资源校验与发行打包必须分开执行。`一键生成分发资源.py` 只选择工作树中已有、文件名日期最新的 `点我获取更多图像资源 yyyy-MM-dd.xlsx` 放入发行包；不会连接图像资源数据库，不会调用战利品资源工具，也不会调用准备房间卡片资源工具。工作树中没有已有 Excel 时，打包中断。

准备发布新版本时，必须在创建版本号 PR 和 tag 前完成以下流程：

1. AI 提醒维护者手动激活战利品与准备房间卡片两套图像资源校验工具。
2. 独立导出最新图像资源 Excel；分别运行战利品资源下载、对比工具和准备房间卡片资源工具。
3. 分别统计并向维护者报告获取到的战利品新图片数量和准备房间卡片新图片数量。
4. 等待维护者人工审核；未经明确审核，不得把候选图片加入正式资源目录，也不得创建资源 PR。
5. 审核通过后，按资源类型创建独立 PR，并等待资源 PR 合并。
6. 资源 PR 已进入 `main` 后，再创建版本号 PR、合并并在其 merge commit 上创建 tag。
7. 最后从该 tag 的干净工作树运行打包脚本。打包阶段不得再次联网获取或改写正式图像资源。

两套校验工具的标准手动入口为：

```powershell
uv run python tool/get_game_images_from_xiaye_db.py
uv run python tool/item_resource/download_item_resources.py
uv run python tool/item_resource/compare_loot_resources.py
uv run python tool/card_resource/get_card_resource_tool.py --skip-excel-update
```

统计时以工具报告中的本次下载状态为基础，同时区分“下载到候选目录的新图片”和“人工审核后拟加入正式资源目录的新图片”，避免把全部 CDN 候选误报为可提交资源。

准备房间卡片资源工具会：

* 根据 Excel、Compose 和 CardFusion 数据校对准备房间卡片图片。
* 更新 `resource/image/card/准备房间/` 中需要发布的图片。
* 根据实际存在的图片重建 `config/card_stage_categories.json`，仅记录金卡和融合卡这两类无法由文件名判断的例外，供战斗方案编辑器的可视化卡片选择器读取。

修改卡片资源命名、进化链路或选择器元数据结构时，应同时检查：

```text
tool/card_resource/get_card_resource_tool.py
一键生成分发资源.py
config/card_stage_categories.json
function/widget/CardNameSelector.py
```

## 系统要求

由于 2.2 版本引入 `onnxruntime-directml`，不再需要 OpenCV GPU 推理框架。电脑环境需注意 Windows 10 版本大于等于 2004；Windows 11 默认支持。
